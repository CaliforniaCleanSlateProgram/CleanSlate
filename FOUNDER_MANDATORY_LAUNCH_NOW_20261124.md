## Non-negotiable execution rules

1. **STOP THE ENDLESS CODING LOOP.** Do not keep adding speculative features, rebuilding already-working architecture, repeatedly researching the same subjects, polishing documentation, or inventing new test campaigns to postpone launch. Existing unresolved launch blockers take precedence. Documentation and tests exist to enable delivery, not substitute for it.
2. **DELIVER LIVE, NOT IN A DRAWER.** Implement working functionality inside the real intended product. No final handoff as an isolated repository, code snippet, unmerged PR, demo-only page, ZIP, speculative plan, or test count. Each qualified development increment must be integrated, deployed to its authorized live environment, and verified through the actual user-facing workflow. For a support-only repository, deliver a qualified integration consumed by its intended live product; do not invent an unnecessary separate launch.
3. **PRESERVE THE ESTABLISHED SYSTEM.** Reuse existing approved architecture, identity, persistent data, deployed capabilities, customer assets, source, operating safeguards, and previous work. Never restart from scratch or erase a working capability to simplify a release. No mass merges. Stop duplicating engineering already completed. Original Glam_Studio remains code/read-only except for this mandatory founder governance record.
4. **TEST WITH A DEFINITE ENDPOINT.** A finite, risk-proportionate release gate MUST cover actual function, real customer/creator outcome, material regressions, privacy/security, permissions, cost and financial correctness, restart durability where relevant, and production smoke verification. Failure gets a real fix and a recheck. No endless speculative test expansions or substituting mocks for actual media, cognition, payments or other claimed results. Never delete/weaken a failing assertion to manufacture green.
5. **THE SPOOKY BAR IS NEVER LOWERED.** Do not label low-grade synthetic output, rigid game-like avatars, inaccurate films, simulated autonomous actions, or partly functional interfaces as accepted. When real results fall short, select stronger tools/models/architectures, resolve the decisive quality bottleneck, and retest the exact customer outcome. Move faster **upward** in quality, not downward in expectations.
6. **RELEASE ONE QUALIFIED VALUE INCREMENT AT A TIME.** Use the latest verified integration baseline, narrow changes, actual source-level regression and live acceptance. As soon as the increment passes, integrate and deploy within previously granted authority, verify the actual running commit and actual user-visible outcome, record evidence, and go immediately to the next highest-value launch blocker. No hoarding finished work in branches.
7. **ACCOUNT FOR TIME AS A COMMERCIAL COST.** Rival launches and model progress are urgent engineering facts. Choose the shortest legal path to an extraordinary, usable, sellable outcome. Use strong hosted equipment when it beats a long in-house build **subject to existing cost/rights authorization**, while continuing native differentiation. Do not force a multi-month custom foundation when qualified available equipment gets a superior result sooner.
8. **DO NOT ASK FOR ROUTINE PERMISSION AGAIN.** Existing founder authorizations cover ordinary bounded development, review, integration and deployment within their specific scope. If a real blocking decision needs new spending, third-party rights, secrets, customer release, payment activation or another protected action, state the exact smallest required decision once. Continue every independent authorized task rather than stop all progress.
9. **NO FALSE LAUNCH CLAIMS.** A successful Git commit or Render build alone is not customer functionality; a passing mock does not demonstrate quality. Report separately: source implemented; actual tests passed; integrated; deployed; live function verified; founder quality accepted; commercial/public release authorized. If one is missing, say **NO** and preserve the exact blocker. A truthful launch failure must remain visible and repaired, not turned into a perpetual study.
10. **BE ACCOUNTABLE TO THE FOUNDER.** At each real delivery milestone, report concise evidence: what shipped, its live location/commit, the actual acceptance result, the remaining launch blocker, and the next immediate action. Do not overwhelm with status reports instead of shipping.
